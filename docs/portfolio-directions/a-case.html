Case study / Earlier work / Coursework

A small language.
A readable parser.

Building a compiler front end in C, with a direct relationship between the grammar and the code that recognizes it.

Role · Course project authorLanguage · CScope · Lexer, parser, IR

01 / Context & constraints

Make the language rules executable.

For a programming languages course, I built a front end that tokenizes input, checks its grammar, tracks identifiers and reports syntax errors. A follow-on part emitted an intermediate representation with simulated register allocation.

The implementation had to be C. That meant allocating identifier buffers, managing their lifetime and implementing a symbol table without the C++ standard library.

02 / Architecture

The call structure follows the grammar.

Each nonterminal has a parser function. Expressions call terms, terms call factors, and parenthesized factors re-enter expression parsing. That nesting gives multiplication precedence over addition.

expression → term { ('+' | '-') term }
term       → factor { ('*' | '/') factor }
factor     → identifier | number
           | '(' expression ')'
Inspect symbol-table responsibility

A hand-written hash table uses buckets and chaining for collisions. Lookup happens at each identifier reference. Explicit allocation and cleanup are part of the implementation, not services provided by the language runtime.

03 / Decisions & tradeoffs

One error, precisely located.

All syntax-error reporting funnels through the match function. On a mismatch it reports the expected token, line and column, frees the symbol table and exits.

The cost is one error per run. Panic-mode recovery could report more errors, but would also require synchronization rules and care to avoid misleading follow-on diagnostics.

Why recursive descent?

One function per nonterminal is straightforward to read and debug for this small grammar. It cannot directly handle left recursion, and changing the language means changing C source. Those limits were acceptable for fixed coursework scope.

Why a hash table?

Identifiers are looked up repeatedly. A chained hash table avoids a full list scan for every lookup, at the cost of managing buffers, buckets and collision chains explicitly.

04 / Outcome & limits

A working front end, with a clear boundary.

The lexer and parser handle comments and multiline statements, track identifiers and report syntax errors with line and column. The second part emits three-address statements over virtual registers.

This is coursework, not a production compiler. There is no optimization pass and register allocation does not target real hardware. A larger, changing language would justify revisiting the parsing strategy.
